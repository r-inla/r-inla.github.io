sTiles

A high performance sparse Cholesky backend for INLA

What is sTiles?

sTiles is a high performance framework for the Cholesky factorization of large sparse symmetric positive definite matrices, developed at KAUST. It tiles the matrix and schedules the factorization over the tiles, which lets it exploit the semisparse structure (sparse blocks combined with dense blocks) that is typical of the precision matrices of latent Gaussian Markov random fields, exactly the matrices INLA factorizes in its inner loop.

Inside INLA, sTiles is available as an alternative sparse matrix backend. The model specification, the calls and the results are unchanged; only the numerical engine that factorizes the precision matrices is different. On structured models (spatial, spatio-temporal, survival and genetics applications among others) this can reduce the factorization time substantially, in particular on machines with many cores.

Using sTiles with INLA

Recent INLA testing builds ship with the sTiles backend included. The easiest way to set everything up is the installer helper, which downloads an INLA binary paired with a matching sTiles library for your platform and selects it for the current session:

library(INLA) inla.stiles.install()

The helper prints the two inla.setOption() lines it applied; put them in your ~/.Rprofile to make the selection permanent. To select the backend by hand in a build that already includes sTiles:

inla.setOption(smtp = "stiles")

You can check what is currently active, and whether the installed binary responds, with:

inla.stiles.status()

Choosing the tile type: sparse, semisparse or dense

sTiles stores the factor as a grid of tiles, and each matrix is handled in one of three tile storage modes. The mode is set per model through control.stiles:

result <- inla(formula, data = data, control.stiles = list(tile.type = "auto"))

Valid values for tile.type are "default", "auto", "sparse", "semisparse" and "dense". With "auto", sTiles inspects the precision matrix (its fill ratio, tile occupancy and degree structure) and picks the mode by heuristics; this is the recommended setting, and the explicit values are there for experimentation. As a rule of thumb: sparse wins on very sparse irregular problems where most tiles never fill in, semisparse wins on the structured latent GMRF precision matrices INLA typically produces (spatial and spatio-temporal models with fixed effects), and dense wins when the reordered factor fills almost completely, as in genetics models with dense relationship matrices. When in doubt, leave tile.type = "auto" and let the heuristics decide per matrix.

The dense mode also removes a classical restriction: the precision matrix does not have to be sparse at all. If it fits in memory, sTiles factorizes it as a tiled dense matrix with BLAS level 3 kernels, so models with fully dense precision matrices can be run through INLA when enough memory is available.

Setting verbose = TRUE in control.stiles prints what sTiles decided, which is useful when comparing modes on your own model.

Notes

Every INLA build that includes sTiles is paired with a specific sTiles release, built with the same compiler and CPU target; the pairing is recorded in the build information shipped with the binaries. The inla.stiles.install() helper always fetches a matching pair, so no manual version bookkeeping is needed.
